# EduTutor v1.8 诊断测评、学习目标与个性化计划设计

日期：2026-11-22
状态：已确认，待实现

## 1. 背景与目标

v1.7 已完成教材、知识版本、来源追踪、审核、激活、回滚、回答证据和纠错治理。v1.8 在这些受控知识之上建立学生首次进入产品时的完整闭环：

1. 设置可版本化的学习目标。
2. 完成绑定知识点和来源证据的诊断测评。
3. 区分“暂无证据”和“已有证据但未掌握”。
4. 根据目标、先修关系、已确认掌握证据和时间约束生成可解释周计划。
5. 在目标或诊断变化后保留旧计划，并显式生成新版本。

首个可复现样例使用当前 active 的二年级下册数学知识版本 `v142`。领域模型和服务保持通用，但 v1.8 不扩展其他教材内容包。

## 2. 范围与边界

### 2.1 本版包含

- 完整纵向闭环：目标设置、诊断、诊断报告、计划生成、关键前端页面、迁移、测试和验收文档。
- 诊断题落库，并通过可复现脚本导入样例；运行时不临时生成题目。
- 客观题确定性判分。
- 主观题由模型生成评分建议，学生确认或修改后才形成有效证据。
- 计划按周分阶段，每项包含预计分钟、推荐原因、知识点和完成条件。
- 目标、诊断和计划历史版本可追踪。
- 复用 v1.7 active 知识版本、来源块和图谱关系；复用既有掌握记忆、错题和复习证据。

### 2.2 本版不包含

- 教师复核流程；教师角色和教师确认留到 v2.3。
- 具体到某一天的任务排程；日任务中心留到 v1.9。
- 普通练习、订正、再练闭环；这些属于 v1.9。
- 运行时模型出题或未经审核的题目自动发布。
- 其他教材内容包扩展。
- 把工程验收样例表述为教师审定题库或真实学习效果证明。

## 3. 方案选择

采用独立的 v1.8 领域模型，不扩展 `Memory`、`ReviewPlan` 或 `WrongQuestion` 来承载诊断语义。

原因如下：

- 诊断中的“未测”“答错”“模型建议待确认”和普通练习失败不是同一种事实。
- 目标和计划需要不可变版本，现有表无法清晰表达版本依据。
- 独立边界便于 v1.9 将真实练习闭环接入，而不破坏 v1.8 历史证据。
- 当前项目不需要全事件溯源架构；不可变版本和证据快照足以满足审计要求。

后端新增 `app/services/diagnostics`、`app/services/learning_plans` 等聚焦服务，并通过 `/api/learning/*` 暴露接口。现有知识、记忆、错题和复习服务只作为受控证据来源。

## 4. 数据模型

### 4.1 学习目标

#### `learning_goals`

保存目标身份、`student_id`、当前版本引用和创建时间。目标身份不随修改而改变。

#### `learning_goal_versions`

每次创建、修改、暂停、恢复或结束都追加新版本。字段至少包括：

- `goal_id`
- `version_no`
- `target_date`
- `weekly_minutes`
- `subject`
- `target_level`
- `status`：`active`、`paused` 或 `ended`
- `change_reason`
- `created_at`

#### `learning_goal_targets`

关联一个目标版本与其目标知识点。知识点必须属于该目标版本固定的 active 知识版本。

### 4.2 诊断题与诊断会话

#### `diagnostic_questions`

题目一经发布即视为不可变。需要修订时创建新记录，避免历史诊断被修改。字段至少包括：

- `knowledge_version_id`
- `knowledge_point_id`
- `source_chunk_id`
- `question_type`：客观题或主观题
- `difficulty`
- `stem`
- `options_json`
- `answer_key_json`
- `rubric_json`
- `max_score`
- `status`
- `created_at`

样例导入脚本只接受 active `v142` 中、具有来源块且没有 provenance gap 的知识点。脚本通过稳定字段查找知识点，不硬编码数据库 ID。

#### `diagnostic_sessions`

保存一次诊断及其固定依据：

- `student_id`
- `goal_id`
- `goal_version_id`
- `knowledge_version_id`
- 状态和开始、提交时间
- 本次选择的题目快照或固定题目关联

同一学生和目标版本存在未完成诊断时，默认返回原会话继续作答。

#### `diagnostic_answers`

每题一条答案记录，保存：

- 原始答案
- 用时
- 自信度
- 客观题确定性得分和判分依据
- 主观题模型建议分、建议依据和模型元数据
- 学生最终确认分、修改理由和确认时间

主观题的模型建议与学生最终确认同时保留。未确认的主观题不能进入诊断结果。

#### `diagnostic_knowledge_results`

按诊断会话和知识点保存聚合结果、得分率、有效题数、掌握等级、证据状态和关联答案 ID。没有有效答案时不创建失败结论；查询层返回 `no_evidence`。

### 4.3 学习计划

#### `learning_plan_versions`

每次生成或重算都创建不可变版本。保存：

- 学生、目标和目标版本
- 使用的诊断会话
- 固定知识版本
- 计划状态和可行性
- 调整原因
- 总可用分钟、已排分钟、缺少分钟
- 证据快照
- 创建时间

#### `learning_plan_items`

保存周次、周内顺序、知识点、预计分钟、推荐原因、完成条件、证据引用和是否排入计划。容量不足且无法排入的候选知识点仍应出现在生成结果的未排入清单中。

## 5. 核心语义

### 5.1 知识版本固定

目标创建时固定当时的 active 知识版本。诊断会话固定目标版本和知识版本；计划固定目标版本、诊断会话和知识版本。active 版本随后变化不能篡改历史。

如果新诊断开始前 active 版本已切换，系统要求创建兼容的新目标版本。已经开始的诊断仍按原版本完成。

### 5.2 暂无证据不等于不懂

只有至少一个已最终判分的有效答案，才能形成该知识点的诊断掌握结论。没有覆盖或答案尚未确认时返回 `no_evidence`，不得写入“不懂”或“薄弱”。

计划可以把无证据知识点标记为“建议基础学习或后续补测”，但不能把它作为失败事实。

### 5.3 掌握度规则

诊断按题目最大分聚合：

- 得分率 `< 50%`：不懂
- 得分率 `50%～79%`：基本会
- 得分率 `≥ 80%`：熟练
- 无有效答案：`no_evidence`

单次诊断不能直接判定“精通”。精通只能由后续真实练习和长期证据支持。用时与自信度用于报告解释，本版不将其加入得分公式。

### 5.4 多来源证据解析

计划生成同时读取：

- 最新已完成诊断结果
- 现有掌握记忆
- 未掌握错题
- 到期复习任务
- 知识图谱前置关系

诊断与既有掌握事实冲突时，采用时间更晚的已确认事实作为当前计划依据；证据快照仍保留冲突双方的来源 ID 和时间。无法比较时采用更保守的掌握等级，并在推荐原因中说明证据冲突。

## 6. 端到端流程

### 6.1 设置目标

`POST /api/learning/goals` 创建目标和首个版本。后续修改、暂停、恢复和结束统一追加目标版本。服务端校验学生归属、目标日期、每周分钟数、目标状态和目标知识点所属版本。

### 6.2 开始诊断

`POST /api/learning/diagnostics` 接收目标 ID：

1. 读取当前目标版本。
2. 收集目标知识点及限定深度内的前置知识点。
3. 从同一知识版本的已发布题目中确定性选题。
4. 固定题目、目标版本和知识版本。

关键知识点没有可用题目时返回缺失知识点清单，不临时调用模型补题。

### 6.3 保存答案与提交诊断

每道答案单独持久化，刷新后可继续。客观题提交后确定性评分，但诊断完成前不向学生泄露标准答案。主观题先保存原答案，再生成评分建议；模型失败时保留答案并允许单题重试。

提交诊断前必须满足：

- 所有已选题目均已作答。
- 所有客观题均完成确定性判分。
- 所有主观题均由学生确认最终得分。

提交操作幂等；重复请求返回同一完成结果。

### 6.4 生成计划

`POST /api/learning/plans` 使用目标版本、最新完成诊断和当前学习证据：

1. 按前置知识图谱拓扑排序候选知识点。
2. 解析每个知识点的当前证据状态。
3. 跳过已熟练且没有错题、到期复习或冲突证据的非目标节点。
4. 为保留项生成推荐原因、预计时长和完成条件。
5. 按周容量和目标日期装入计划。

目标知识点始终保留。容量不足时不能静默突破时间限制；返回 `needs_adjustment`、缺少分钟数和未排入项，提示延长目标日期或增加每周投入时间。

目标版本或诊断结果变化后，现有计划被查询层标记为过期。用户显式点击重新生成后创建新计划版本，调整原因记录为 `goal_changed`、`diagnostic_retake` 等稳定枚举。

## 7. API 边界

接口统一位于 `/api/learning`，至少覆盖：

- 创建、查询和追加学习目标版本
- 暂停、恢复和结束目标
- 创建或继续诊断会话
- 查询诊断题与进度
- 保存答案
- 请求或重试主观题评分建议
- 确认主观题得分
- 提交诊断并查询报告
- 生成或重算计划
- 查询当前计划、过期状态和版本历史

所有接口复用现有登录态和 `get_owned_student` 所代表的学生归属校验。资源 ID 不能绕过学生归属检查。

## 8. 前端设计

侧边栏新增“学习计划”，路由到单一 `LearningPlanView.vue`。页面按四阶段组织：

### 8.1 学习目标

选择学生，填写目标日期、每周分钟、目标水平和 `v142` 目标知识范围。展示当前目标版本，并提供修改、暂停、恢复和结束操作。

### 8.2 诊断测评

一次显示一道题。答案提交后显示保存状态；刷新后恢复未完成会话。主观题展示模型建议和依据，要求学生确认或修改。

### 8.3 诊断报告

按知识点展示“暂无证据、不懂、基本会、熟练”、得分、用时、自信度和来源页。页面必须用不同文案与视觉状态区分“未测到”和“测过但未掌握”。

### 8.4 周学习计划

按周分组展示计划项、预计分钟、前置关系、推荐原因、完成条件和证据引用。版本历史抽屉允许查看旧计划和调整原因。

现有“智能出题”页保持普通练习语义，本版不把它改造成诊断入口。

## 9. 异常处理与恢复

- 同一目标版本存在未完成诊断时默认续答，不重复创建。
- 每题答案独立保存，重复提交幂等更新同一记录。
- 主观评分失败不丢答案，并提供单题重试。
- 诊断提交条件未满足时返回结构化缺失项。
- 计划生成遇到图谱缺口时保留目标知识点并返回证据缺口，不推测不存在的前置关系。
- 目标或诊断变化后保留旧计划，只标记过期。
- 容量不足时明确返回缺少时间和未排入知识点。
- 前端请求失败时保留当前表单或答案状态，并显示可执行的重试提示。

## 10. 测试策略

所有行为变更采用测试先行：先写一个最小失败测试，确认因目标能力缺失而失败，再写最小实现使其通过，最后在全绿状态下重构。

### 10.1 后端测试

- 目标创建、修改、暂停、恢复和结束均产生不可变版本。
- 目标和诊断资源执行学生归属校验。
- 诊断只使用固定知识版本内、已发布且有来源证据的题目。
- 客观题重复判分一致。
- 主观题未确认时不能提交或形成掌握证据。
- 未覆盖知识点为 `no_evidence`，不会落成“不懂”。
- 重测产生新结果，不覆盖旧结果。
- 计划保持前置拓扑顺序，并遵守周分钟和目标日期。
- 证据冲突、图谱缺口和容量不足返回可解释结果。
- 目标或诊断变化使旧计划过期，重算产生新版本。
- 完整 API 集成测试跑通“新学生 → 目标 → 诊断 → 报告 → 计划”。

### 10.2 前端测试

- 目标表单校验和版本操作。
- 诊断续答、答案保存和主观题确认门禁。
- “暂无证据”与“测过但未掌握”的不同展示。
- 计划过期、容量不足和版本历史。
- API 失败后保留用户输入并允许重试。

### 10.3 工程门禁

- Alembic 空库升级、降级和再升级通过。
- 后端目标测试和完整测试通过。
- 前端组件测试、类型检查和生产构建通过。
- 样例脚本生成完整诊断报告和计划 JSON。
- 运行结果写入 `docs/releases/v1.8/acceptance.md`，不预填或编造通过数字。

## 11. 验收产物

- v1.8 Alembic 迁移。
- 目标、诊断和计划的模型、服务与 API。
- “学习计划”完整前端页面及 API 类型。
- `v142` 诊断题可复现导入脚本。
- 迁移往返检查脚本。
- 样例诊断报告和计划 JSON。
- 后端和前端自动化测试。
- `docs/releases/v1.8/acceptance.md`。

验收通过的定义是：一个没有历史记忆的新学生无需手工修改数据库，即可完成“设置目标 → 诊断 → 查看报告 → 生成计划”；系统正确区分无证据与未掌握，计划能够解释先修关系、当前证据和时间约束，重测或修改目标后仍保留全部历史版本。
