# EduTutor v1.7 教材、知识库治理与回答证据设计

日期：2026-10-15  
状态：已确认，待实施计划  
范围：完整 v1.7，包含最小管理界面与 `admin` 权限

## 1. 目标与成功标准

v1.7 要把“教材进入系统、知识库发布、回答引用证据、错误反馈修正”做成可审计闭环。它不以知识点数量为完成标准，而以一册真实教材能够完成以下流程为准：

```text
上传 → 预检 → 可恢复编译 → staged 版本 → 抽检 → 激活
     → 回答引用 → 纠错 → 修订版本 → 回滚 → 再激活
```

版本完成时必须满足：

- 教材元数据、文件哈希、来源和授权说明可查询。
- 构建任务可观察、可续跑、可单独重试失败单元，重复文件不产生重复有效数据。
- staged 数据不会进入学生回答；只有审核通过的版本可以激活。
- 每条教学回答能回溯到知识点、记忆、检索摘要和教材来源页。
- 证据不足时返回明确的知识缺口，不根据模糊画像补造教材事实。
- 用户反馈先进入纠错队列，不能直接覆盖教材、知识版本或历史对话。
- 至少一册教材完成激活、回滚和再激活的真实验收。

## 2. 范围边界

### 2.1 本版包含

- `user/admin` 最小角色能力和管理员接口保护。
- 教材、构建任务、构建单元、知识版本、来源块、抽检、证据账本和纠错工单的持久化模型。
- PDF 安全上传、SHA-256 去重和本地受管文件存储。
- 以 MySQL 为状态源的轻量 worker、任务租约、检查点、续跑和失败重试。
- 版本化知识点、图谱边与 Chroma 向量，审核、激活和回滚。
- active 知识检索、回答证据、知识缺口和流式/非流式接口一致性。
- 管理员教材治理页面，以及学生聊天页的教材证据和反馈入口。
- 迁移、后端测试、前端测试与构建、双库审计和 v1.7 验收记录。

### 2.2 本版不包含

- Redis、Celery、微服务或分布式任务调度。
- 教师、家长等完整角色体系；这些仍属于 v2.2～v2.3。
- 一次性编译全部教材或宣称全学段、全学科完成。
- 自动信任用户纠错、直接重写历史消息或原始教材。
- 评测集扩充和新的学习效果指标；统一评测仍属于 v2.4。
- 自动删除历史版本及其向量；历史保留用于审计、旧引用和回滚。

## 3. 核心架构

采用“不可变知识版本 + 教材活跃指针”。每次完整构建或教材修订都产生新版本，已有版本不原地修改。教材通过 `active_version_id` 指向当前发布版本。

```text
Vue 管理界面
  → FastAPI 管理接口
    → MySQL 教材/任务/版本/审核状态
      → CLI worker 认领任务
        → PDF 解析/OCR
        → LLM Wiki 编译
        → MySQL staged 知识点与来源
        → Chroma staged 向量
          → 一致性检查与人工抽检
            → 切换 active_version_id
```

学生回答链路同时使用两个相互独立的证据源：

```text
学生问题
  ├─ 长期记忆检索 → 记忆 ID 与四项融合分数
  └─ active 知识检索 → 知识点、版本、来源块、页码与相似度
       → 证据充分性判断
       → LLM 生成
       → 助手消息 + 不可变证据账本
```

## 4. 数据模型

### 4.1 用户角色

`users` 增加：

- `role`：`user` 或 `admin`，非空，默认 `user`。

注册用户始终为 `user`。首个管理员通过显式 CLI 命令设置，不由迁移脚本猜测或批量提权：

```powershell
python scripts/set_user_role.py <用户名> admin
```

### 4.2 教材与构建

`textbooks` 保存：

- 学段、年级、学科、出版社、版次、册次；
- 原文件名、受管相对路径、MIME、字节数、页数、SHA-256；
- 来源 URL 或来源说明、授权说明；
- 上传人、创建时间、`active_version_id`；
- `source_kind`，正常上传为 `uploaded`，历史回填为 `legacy`。

SHA-256 全局唯一。教材身份由“学段 + 年级 + 学科 + 出版社 + 版次 + 册次”确定。同一文件再次上传时返回已有教材记录；同一教材身份上传不同文件，或同一哈希提交冲突元数据时，接口返回冲突详情，不静默覆盖。v1.7 不处理同一教材的源文件换版；真正的新教材必须使用可区分的版次元数据。

`knowledge_build_tasks` 保存：

- 教材、目标版本、请求人、幂等键；
- 总体状态、当前阶段、进度计数；
- worker 租约拥有者、租约过期时间、心跳时间；
- 重试次数、错误摘要、创建/开始/结束时间；
- 实际解析器、OCR、提示词、LLM 和嵌入模型版本。

`knowledge_build_units` 保存每个可恢复处理单元的：

- 单元类型（逐页提取、页组编译或向量索引）、顺序、起止页、状态、尝试次数；
- 输入内容哈希、检查点、错误类型和错误详情；
- 开始/完成时间。

逐页提取与页组编译使用不同单元，因此某一页解析失败时可以只重试该页；某个页组的 LLM 编译失败时也只重试对应页组。

`knowledge_build_events` 作为追加式任务日志，保存任务、单元、级别、阶段、消息和时间。状态查询只读取结构化任务字段；日志用于诊断和验收，不通过解析日志文本推断任务状态。

### 4.3 版本与来源

`knowledge_versions` 保存：

- 教材、版本号、来源构建任务、父版本；
- `building/staged/active/archived/rejected` 状态；
- 知识点数、图谱边数、来源块数、向量数；
- 创建、审核、激活时间和操作者。

任一教材最多有一个 active 版本。激活新版本时旧 active 版本变为 archived；回滚是把指定历史版本重新激活，而不是重新导入数据。

由于当前学生画像只有年级和学科、尚未选择出版社或教材版次，v1.7 进一步规定同一“年级 + 学科”学习范围最多只能有一个 active 知识版本。激活另一册同范围教材时，服务端在同一事务内归档旧版本并清空旧教材的 active 指针。后续 v2.1 内容包发布时再把选择范围扩展为明确的教材包。

`knowledge_source_chunks` 保存：

- 版本、来源文件、起止页、页内区域；
- 原始文本、内容哈希、解析方式和解析器版本；
- 构建单元与顺序。

文字版 PDF 尽量保存 PyMuPDF 文本块坐标。OCR 无法可靠定位时区域允许为空，但必须保留页码、解析方式和真实 OCR 版本。

`knowledge_points` 增加：

- `version_id`、`source_chunk_id`；
- 来源摘录及来源缺口标记。

图谱边通过两端知识点归属版本。服务层禁止创建跨版本边，除非未来增加显式跨版本关系类型；v1.7 不开放这种类型。

### 4.4 审核、证据与纠错

`knowledge_reviews` 保存版本级审核人、结论、说明和时间。  
`knowledge_review_items` 保存抽检类型、目标、原值、结论和修正意见。抽检类型至少包括正文、公式、知识点、难度和先修关系。

`answer_evidence_ledgers` 与助手消息一对一，保存：

- 学生、会话、助手消息；
- 知识候选与采用项，包括知识点、版本、来源块、页码和相似度；
- 记忆候选与采用项，包括记忆 ID 和融合分数摘要；
- 实际检索配置、证据缺口状态与原因；
- 创建时间。

候选明细使用结构化 JSON 快照保存，保证将来版本切换后仍能解释历史回答；关键外键另列保存，便于查询和完整性检查。

`correction_tickets` 保存：

- `knowledge/question/explanation/memory` 分类；
- 目标类型、目标 ID、原值快照、建议值、原因；
- `pending/accepted/rejected/applied` 状态；
- 提交人、处理人、处理说明和各阶段时间；
- 应用纠错后形成的版本 ID 或记忆变更引用。

## 5. 现有数据迁移

现有知识点和关系不得被删除，也不得伪造教材来源。迁移按已有 `subject + grade` 分组创建只读的 legacy 教材和 active legacy 版本，并把对应知识点关联过去。

- 出版社、版次、册次、来源文件、页码和授权未知时保持空值。
- legacy 知识点设置 `provenance_gap=true`。
- 原有知识向量补写 `version_id`、`textbook_id` 和 legacy 标志 metadata。
- legacy 数据仍可用于现有功能，但回答证据必须展示“历史导入，缺少教材页来源”。
- 新教材版本激活后，只替代同一教材记录的旧版本；不同 subject/grade 分组之间互不影响。

迁移必须实际验证 upgrade、downgrade、再次 upgrade。数据回填脚本应可重复运行并报告处理数量，不能重复创建 legacy 记录。

## 6. 构建任务状态机

总体状态与当前阶段分开：

```text
queued
  → running/precheck
  → running/extract
  → running/compile
  → running/index
  → succeeded（目标版本进入 staged）
```

异常路径：

```text
running → needs_attention → queued
running → failed
queued/running → cancelled
```

规则：

- 空白页记为 `skipped`，不算失败。
- PDF 损坏、OCR 失败、LLM 非法结构和向量写入失败必须保留错误类型与上下文。
- 存在未处理失败单元时，任务只能进入 `needs_attention`，不能生成 staged 版本。
- `resume` 从未完成单元继续；`retry-failures` 只重置失败单元。
- worker 通过原子更新认领任务并定期续租。租约过期后其他 worker 可以重新认领。
- 单元完成后立即提交检查点；幂等写入由任务 ID、单元 ID 和内容哈希共同约束。
- DeepSeek、BGE-M3 或 OCR 未真实加载时明确失败，不把回退结果登记为对应模型结果。

worker 以独立命令运行：

```powershell
cd backend
python scripts/knowledge_worker.py
```

这保持 API 请求短暂、任务状态持久，又避免在无负载依据时引入 Celery 或 Redis。

## 7. 发布、一致性与回滚

staged 版本在构建期间使用全新知识点和向量 ID，不覆盖 active 版本。激活前必须通过：

1. 所有构建单元完成，无未处理失败。
2. 知识点、来源块、图谱边外键完整。
3. MySQL 知识点数量与 Chroma 对应版本向量数量一致。
4. Chroma metadata 中教材和版本标识正确。
5. 版本级审核结论为通过，必需抽检类型齐全。

激活与回滚接口要求调用方提交 `expected_active_version_id`。服务端在事务内锁定教材记录并比较当前值；不一致返回 `409`，防止并发管理操作丢失更新。

查询时先从 MySQL 得到匹配教材的 active 版本 ID，再用这些 ID 过滤 Chroma。由此：

- staged 和 rejected 版本不会进入回答；
- 回滚只切换 MySQL 指针，不重建向量；
- 历史消息的证据快照不受当前 active 版本变化影响。

历史版本和向量在 v1.7 不自动删除。删除策略必须在未来版本单独设计，不能作为上传或激活的副作用。

## 8. API 设计

### 8.1 管理员接口

所有 `/api/admin/*` 接口要求 `admin`：

- `POST /api/admin/textbooks`：multipart 上传 PDF 与元数据。
- `GET /api/admin/textbooks`、`GET /api/admin/textbooks/{id}`：列表与详情。
- `POST /api/admin/textbooks/{id}/builds`：创建构建任务。
- `GET /api/admin/builds`、`GET /api/admin/builds/{id}`：任务列表与进度。
- `POST /api/admin/builds/{id}/resume`：从检查点续跑。
- `POST /api/admin/builds/{id}/retry-failures`：只重试失败单元。
- `POST /api/admin/builds/{id}/cancel`：请求取消未完成任务。
- `GET /api/admin/versions/{id}`：版本、知识点、来源与图谱概要。
- `POST /api/admin/versions/{id}/reviews`：提交抽检。
- `POST /api/admin/versions/{id}/activate`：审核后激活。
- `POST /api/admin/textbooks/{id}/rollback`：切回指定历史版本。
- `GET /api/admin/corrections`：纠错列表与筛选。
- `POST /api/admin/corrections/{id}/accept`：接受并产生受控变更。
- `POST /api/admin/corrections/{id}/reject`：填写原因后驳回。

### 8.2 用户接口

- `POST /api/corrections`：登录用户提交反馈，服务端生成原值快照。
- `GET /api/knowledge/evidence/{assistant_message_id}`：消息归属校验后读取证据账本。
- `/api/chat`：在兼容原字段的基础上返回知识证据、记忆证据和缺口状态。
- `/api/chat/stream`：增加 `knowledge_retrieved` 与 `evidence_recorded` 事件。

流式和非流式回答必须调用同一检索与证据服务，不能维护两套评分和缺口规则。

## 9. 回答证据与知识缺口

知识检索按学生 `subject + grade` 选择 active 版本，以 BGE-M3 相似度召回知识点，并返回来源块。知识候选和长期记忆候选分别评分，不能把两类分数混成不可解释的总分。

证据充分性至少检查：

- 是否存在匹配学科和年级的 active 版本；
- 是否存在达到配置阈值的知识候选；
- 候选是否具有可用正文；
- 来源是否完整，或是否为明确标识的 legacy 缺口。

当问题明显要求教材事实而上述条件不满足时，设置 `evidence_gap=true`。系统提示词要求模型明确说明当前知识库缺口，并可给出通用解题建议，但不能声称建议来自指定教材。

回答正文可使用 `[来源1]` 等标记；来源编号由检索结果确定。无论模型是否正确输出标记，前端都展示服务端证据卡片，因此证据链不依赖模型自由生成引用。

## 10. 纠错语义

- 教材或知识点纠错：从 active 版本创建以其为父版本的完整 staged 快照。未受影响的数据保持相同内容并复用已有嵌入结果，受影响内容重新编译和索引；重新审核后才能激活。新版本不通过外键依赖父版本才能完成查询，因此父版本始终可以独立回滚。
- 回答或讲解纠错：保留原助手消息与证据账本，在工单中记录问题和处理说明，不改写历史对话。
- 记忆纠错：管理员接受后调用现有记忆编辑流程，同时在工单保存前后快照和结果引用。
- 题目纠错：v1.7 保存和审核工单；若目标属于现有错题或出题记录，只能通过对应服务产生新记录或受控更新，不伪造历史作答。完整题目版本化属于 v1.9。
- 驳回必须填写原因。接受后若应用失败，工单保持 `accepted` 并记录失败，不伪装为 `applied`。

## 11. 前端设计

认证用户信息增加 `role`。路由和菜单根据角色隐藏管理入口，但真正授权始终由后端执行；直接访问管理路由时，普通用户跳回业务页面并显示无权限提示。

新增“教材治理”页面，包含四个标签页：

1. **教材**：上传 PDF，填写教材与来源许可信息，查看哈希、当前 active 版本和历史版本。
2. **构建任务**：显示阶段、进度、租约状态、失败单元和日志，提供续跑、失败重试和取消。
3. **版本审核**：浏览抽样来源块、知识点和关系，记录正文、公式、难度、先修关系检查，执行激活和回滚。
4. **纠错队列**：按状态与类型筛选，对比原值和建议值，接受或填写理由驳回。

聊天页在现有“本轮记忆轨迹”旁增加“本轮教材证据”：

- 展示知识点标题、教材、版本、页码、相似度和 legacy 来源缺口。
- 展示 `evidence_gap` 提示。
- 每条助手回答提供反馈入口，自动绑定消息与证据账本，用户只填写分类、建议和原因。

管理页面以完整演示治理闭环为目标，不扩展成通用运营后台。

## 12. 安全与错误处理

- 仅接受 PDF；校验扩展名、MIME 和文件头，并配置文件大小与页数上限。
- 服务端生成存储文件名，文件只写入 `backend/data/textbooks/` 下的受管目录，拒绝路径穿越。
- 数据库只保存相对路径；API 不返回服务器绝对路径。
- 上传失败时清理未登记的临时文件；已登记文件不随接口错误被静默删除。
- 构建日志不得记录 API Key、密码或完整授权令牌。
- API、worker、迁移和 CLI 的错误返回非零退出码或明确 HTTP 状态。
- `401` 表示未登录，`403` 表示非管理员，`404` 用于不存在或不可见资源，`409` 用于哈希元数据冲突、状态冲突和 active 指针冲突，`422` 用于输入校验失败。
- LLM 或向量服务失败不允许产生可激活的半成品。

## 13. 测试策略

所有生产行为遵循测试先行。每个小行为先增加一个能因缺少功能而正确失败的测试，再实现最小代码并运行相关回归。

### 13.1 后端测试

- 用户角色默认值、管理员 CLI、管理接口 `401/403`。
- 文件类型、文件头、大小、路径安全、SHA-256 幂等与元数据冲突。
- 状态机合法与非法转换、任务幂等键。
- worker 租约、心跳、租约过期认领、崩溃恢复、检查点和失败单元重试。
- staged 数据不可检索，active 数据可检索。
- 审核类型门禁、一致性门禁、并发激活 `409`、回滚与再激活。
- Chroma metadata 和版本过滤；失败写入不能通过激活门禁。
- 有证据、低分证据、无 active 版本、legacy 来源缺口。
- 流式与非流式证据结构一致，账本与助手消息关联。
- 纠错不会直接修改教材或历史消息，接受教材纠错产生 staged 子版本。
- Alembic upgrade、downgrade、再次 upgrade，以及 legacy 回填幂等。

数据库和服务层关键行为必须使用真实 MySQL 测试，不能只测试纯函数绕开事务。Chroma 一致性相关用例应使用隔离 collection 或可清理测试 collection。

### 13.2 前端测试

- 普通用户与管理员菜单、路由行为。
- 上传校验和重复文件提示。
- 构建进度、失败单元、续跑与重试交互。
- 审核门禁、激活确认、并发冲突提示和回滚确认。
- 聊天证据卡、知识缺口和反馈表单。
- 纠错队列接受、驳回及失败状态。
- `vue-tsc --noEmit`、Vitest 和 Vite 生产构建。

### 13.3 真实样例验收

选择一册现有教材，实际执行：

1. 上传并记录 SHA-256。
2. 创建任务并启动 worker。
3. 人为中断 worker，验证租约到期后的续跑。
4. 制造一个受控失败单元并单独重试。
5. 完成全部抽检类型并激活。
6. 提问一个有证据问题和一个证据不足问题，核对账本与页面。
7. 提交并处理一条教材纠错，生成 staged 修订版本。
8. 激活修订版本、回滚旧版本、再次激活修订版本。
9. 重复上传同一 PDF，确认没有重复有效数据。

结果写入 `docs/releases/v1.7/acceptance.md`，包括日期、命令、退出码、任务 ID、版本 ID、抽检记录、双库检查结果和已知限制。不预写通过数量，不把模拟结果描述成真实模型结果。

## 14. 实施里程碑

1. 权限、数据模型、迁移与 legacy 回填。
2. 上传、任务状态机、worker、版本化构建和来源追踪。
3. 抽检、激活、回滚及双库一致性门禁。
4. active 知识检索、证据账本、流式/非流式聊天接入。
5. 纠错闭环、教材治理页面和聊天证据界面。
6. 真实教材验收、回归、审计和发布文档。

每个里程碑完成后先运行其专项测试，再运行现有离线回归。除必要的兼容改动外，不夹带与 v1.7 无关的重构。

## 15. 设计决策摘要

- 选择不可变版本和 active 指针，而不是原表批量改状态或 JSON 快照恢复。
- 选择 MySQL 持久化任务与独立 CLI worker，而不是请求内长任务或立即引入 Celery。
- 选择数据库角色字段，而不是依赖 `.env` 管理员名单。
- 选择服务端证据账本和证据卡，而不是信任 LLM 自行生成引用。
- 选择保留并标注 legacy 来源缺口，而不是伪造旧知识点的教材页码。
- 选择纠错产生受控新版本，而不是直接覆盖正式数据和历史记录。
